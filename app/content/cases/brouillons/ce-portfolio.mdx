## Le contexte

Je développe en Ruby on Rails au quotidien, et j'utilise déjà Next.js sur un autre projet (The Rolistes). Pour ce portfolio, j'ai voulu montrer React et TypeScript seuls, sans framework qui fasse le travail à ma place : routes, composants, état, typage, tests et build.

J'ai codé ce site moi-même plutôt que de prendre un constructeur de sites. Son code est public, testé et vérifié automatiquement : il sert lui-même de preuve.

## Le problème

Un portfolio change souvent : nouvelles études de cas, textes réécrits, pages réorganisées. Il fallait un site statique, rapide et lisible avant le chargement du JavaScript, qu'on peut faire évoluer sans casser un lien, une page ou un téléchargement.

## La démarche

**Maquettes d'abord.** J'ai comparé 8 directions graphiques avant d'écrire une ligne de code, puis j'ai intégré celle que j'avais retenue page par page : en-tête, accueil, pages de profil, liste des cas, page d'un cas.

**Une stack simple et maîtrisée.** React 19 et TypeScript en mode strict, React Router 8 et Vite, Tailwind CSS 4, MDX pour les textes.

**Un site prérendu.** Au build, chaque page devient un fichier HTML statique, études de cas comprises. Le contenu s'affiche avant le chargement du JavaScript. Chaque page a son propre titre et son propre aperçu quand on la partage sur LinkedIn. Les liens directs fonctionnent sur un hébergement statique comme GitHub Pages.

**Les tests d'abord, sur les comportements.** Pour chaque changement de comportement, j'écris d'abord les tests, je les vois échouer, puis j'implémente. Ils vérifient ce qui peut vraiment casser : un lien ou une ancre qui ne mène nulle part, un CV absent, une redirection, une donnée invalide, ou un élément sans nom pour les lecteurs d'écran. Un test vérifie par exemple que chaque étude de cas a exactement un fichier de texte : si j'en oublie un, la suite échoue.

**L'intégration et le déploiement continus.** À chaque pull request et à chaque push sur la branche principale, GitHub Actions vérifie les types, le lint, le formatage, lance les tests et fait le build. Si tout passe, un second job publie le site sur GitHub Pages. Chaque job n'a que les droits dont il a besoin.

## Les décisions et les arbitrages

**React Router plutôt qu'Astro.** Astro est fait pour les sites de contenu et aurait sans doute produit un site plus léger. Mais ce site doit aussi montrer que je sais construire une application React : routes, composants, état, typage. React Router en mode prérendu donne les deux à la fois : des pages statiques au premier chargement, puis une application React classique.

**MDX pour les textes, TypeScript pour les métadonnées.** Le titre, le résumé, les tags et l'encadré « En bref » de chaque cas sont typés dans un fichier TypeScript, donc vérifiés par le compilateur. Le texte long est en MDX, plus agréable à écrire et à relire. J'ai écarté un CMS : il aurait ajouté un service à maintenir pour un site que je suis seul à modifier.

**Des polices hébergées avec le site.** Charger les polices depuis Google Fonts aurait été plus simple. Mais cela envoie l'adresse IP du visiteur à un tiers, ce qui pose un problème de RGPD, et ajoute une connexion avant l'affichage. Le site ne fait donc aucune requête vers un tiers sans action du visiteur : une vidéo YouTube ne se charge que s'il clique dessus.

**Rediriger plutôt que supprimer.** Une ancienne page faisait doublon après une refonte de l'accueil, mais son adresse figurait sur des CV imprimés. GitHub Pages ne permet pas de redirection côté serveur : la page prérendue contient une balise `refresh` qui renvoie vers l'accueil même sans JavaScript, et une adresse canonique qui signale l'accueil aux moteurs de recherche.

## Les résultats

- **Plus d'une centaine de tests automatisés** (Vitest et Testing Library), lancés avec la vérification des types, le lint, le formatage et le build.
- **Un site en ligne, publié automatiquement** dès que les vérifications passent.

## Ce que je ferais autrement

**Stabiliser les contenus avant de figer les composants.** J'ai construit les pages avec des textes provisoires. Quand l'accueil a été réorganisé, des composants entiers sont devenus inutiles et une partie de la configuration ne servait plus. C'est le contenu qui décide de la structure, pas l'inverse.

**Ne pas me fier aux seuls tests.** Un jour, une erreur de configuration cassait le build alors que tous les tests passaient : le fichier de configuration est chargé par Node avant Vite, et les tests ne le chargent jamais. Depuis, le build fait partie de chaque vérification, en local comme dans la CI. Les tests disent que le code fait ce que j'attends ; seul le build prouve que le site sort.
